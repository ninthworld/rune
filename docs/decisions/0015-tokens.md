# ADR 0015: What a permanent is, when it is not a card

- Status: accepted
- Date: 2026-07-31

## Context

ADR 0008 built the card model on one idea: a functional definition, authored by hand under
a stable `FunctionalId`, interned to a build-local `CardId`, and read through that handle
by every rules path. `Permanent.card` was a `CardId`, and roughly a dozen modules —
characteristics, combat legality and damage, targeting, state-based actions, the trigger
collector, the view projection, the rules-text formatter — each wrote `db.card(perm.card)`
and got back the `CardData` they needed.

That model has one assumption baked into it so quietly it is easy to miss: **every
permanent is a card**. A token (CR 111) is not. It is a battlefield object whose
characteristics come from the effect that created it, it has no card behind it, and it
ceases to exist the moment it would go anywhere but the battlefield (CR 111.7). No amount
of card data can express one, which is why `exclusions.json` carried "Token creation — no
token object model; every permanent needs a catalog card" and why 22 M19 cards — the
largest single blocked family, across every colour and both creation mechanisms — were
unauthorable.

The tempting shortcut was to author each token as a catalog card and point the permanent at
it. That was rejected outright: a token is not a card, and giving it a `functional_id`
would put a non-card in the compatibility report — the project's central honesty artifact —
and in decklist-legal reach. The object model was the work.

## Decision

**1. A permanent stores where its printed characteristics come from, not a card.**
`Permanent.card: CardId` became `Permanent.printed: Printed`, a two-variant enum:
`Card(CardId)` or `Token(Box<TokenData>)`. The rename is doing as much work as the retype.
Every read of a permanent's printed face became a compile error, so the compiler — not a
reviewer's memory — named all ~40 sites and made each one answer the token question. Adding
an `Option`-shaped field beside the existing `card` would have compiled everywhere and been
silently wrong in the places that mattered.

**2. `Printed::card()` returning `Option<CardId>` is where CR 111.7 lives.** The three
leave-the-battlefield seams (graveyard, exile, hand) each ask for the `CardInstance` to put
in the destination zone, and a token has none to give — so nothing is put anywhere, and the
token ceases to exist. That is one function, `card_leaving`, shared by all three, which is
what makes "a token that dies reaches no graveyard", "a bounced token never arrives in a
hand", and "an exiled token is not in exile" a single fact rather than three that could be
implemented two-thirds of the way. CR 704.5d states the rule as a state-based action over a
token in the wrong zone; the token never gets there, which is the same observable game with
no phantom object to clean up.

**3. The read path is a borrowed union, computed nowhere.** `PrintedFace<'a>` is
`Card(&CardData)` or `Token(&TokenData)`, produced by `Printed::face(db)`, with accessors
for exactly what the rules read: name, types, subtypes, colors, power, toughness, keywords,
restrictions, mana cost, Aura grant, type line. One `match` per characteristic, inside one
module, instead of a token branch in each of a dozen callers. It borrows rather than owns
because a permanent's face is read on every characteristics computation, every combat
check, and every view projection.

Abilities are the deliberate exception: a card's ability set unions the data tier with the
code tier keyed on its authored identity, which a token has not got, so
`abilities_of_permanent` answers that question instead.

**4. A token's death is observed from the recorded event, not from a graveyard.** The
diff-based trigger collector decided "this permanent died" by looking for its card instance
in a graveyard it was not in before. A token can never satisfy that test — and its death is
still real, and CR 603.6c still fires dies triggers on the way out. So `death_of` splits:
a card is judged by the graveyard as before, and a token by the `PermanentDied` event the
one death seam records, read from the same event diff the life-gain and cast conditions
already use (ADR 0007). A bounced or exiled token records no such event and therefore fires
nothing, which is the distinction the graveyard test was providing for cards.

**5. A token carries no authored identity, structurally.** `TokenData` has no
`functional_id` field, no `mana_cost`, no `spell_effects`, no `aura`, no `scripted` — and
`deny_unknown_fields`, so writing one is a parse error. "Tokens do not appear in the
compatibility report" is therefore not a rule anyone has to remember or a filter anyone has
to maintain: the report is generated by walking the catalog, and a token is not in it
because a token cannot be in it.

**6. The creating effect names its creator, rather than assuming it.** `create_token`
carries a `PlayerRef` — the same reference `mill` and `discard` use to name whose library
or hand they act on — so "you create" and "target player creates" are the same effect with
a different subject, and the fizzle rule for the targeting form is inherited rather than
restated. It also carries `count`, `tapped`, and `attacking`, because creation is not
always "one, untapped, out of combat".

**7. The wire says "token" outright.** `CardView.token` is a boolean, additive and omitted
when false, beside the `functional_id` that is empty for a token. Both are needed: the
empty identity is the *symptom* a token shares with a card the server could not resolve,
and the two want opposite treatment — a token is a real object to render normally that
simply has no identity to cache or look art up by (ADR 0012), while an unresolvable card is
a fault. Leaving the client to infer the difference would be asking it to compute a rules
fact, which is the one thing it may not do.

**8. The log records a token's name.** `LoggedPermanent` names its object by `CardId` so
the server can resolve a display name from the catalog. A token has no card, and by the
time anyone reads the entry it has ceased to exist — so `LoggedIdentity` is an enum, and
the token variant carries the name it had. This is the one place a display name reaches the
server from the engine rather than from the catalog, and the alternative — an
`Option<CardId>` — would have every token in every log called "unknown".

## Consequences

Six M19 cards became authorable immediately (Goblin Instigator, Aviation Pioneer, Gallant
Cavalry, Doomed Dissenter, Knightly Valor, Heroic Reinforcements) and are in the catalog.
The remaining sixteen from issue #605 are blocked on primitives that are not about tokens:
a nontoken predicate, a count-derived quantity, sacrifice as a cost, an intervening-if. The
token model makes each of them one primitive away instead of two, and `Printed::is_token()`
is already the first-class predicate three of them need, rather than an absence to be
inferred.

Two creation parameters were deliberately unmodeled here and named in the exclusions, and
the first has since been built as this decision predicted it would be. A token created
**already attacking** (issue #734, Leonin Warleader) is one more entry-state parameter
beside `tapped`, taking its defender from the attack its own source is making rather than
from the card, and CR 506.3c — never *declared*, so no attack trigger fires for it — is
one condition in the diff-based trigger collector rather than a token special case
anywhere. A token created as a **copy** of another permanent is still out, and the reason
has changed. The copiable-values model it was waiting on now exists (issue #734): a copy is
recorded as a handle to a printed face and read at CR 613 layer 1, ahead of every layer the
engine applies, and Mirror Image — a *card* that enters as a copy — is in the catalog. What
is missing is on this side of the line. `create_token` authors a token's characteristics
inline and nothing points one at another permanent's copiable values; and `TokenData` is the
wrong shape for the job anyway, because CR 707.8a gives a token copy of a transforming
permanent *both* faces and the ability to turn over, while a token has exactly one face by
construction (§5 above). Both facts are named in the exclusions.

The cost is that `Permanent` no longer answers "what card is this?" without a `match`. That
is the honest shape: a battlefield object is not always a card, and code that assumed
otherwise was wrong even when it was convenient. The compiler now asks the question at
every site, which is exactly where the CR 111.7 decisions turn out to live.
